# AI 多人协作流程

适用于不同开发者、不同 AI 会话和不同机器共同维护本仓库。按独立任务分工，每个任务使用自己的工作目录和分支，经 Pull Request（PR）测试、审核后合入 `main`，由当轮发布负责人统一打包发布。最新明确的用户要求优先。

## 开始前

1. 阅读根目录 [AGENTS.md](../AGENTS.md)、[AI_README.md](../AI_README.md) 和本文。玩法与测试命令见 [ROGUELIKE.md](ROGUELIKE.md)，发布另读 [RELEASING.md](RELEASING.md)。
2. 检查当前分支、未提交改动、最新 `origin/main` 和相关 Issue / PR，接着已有进度工作。不能清理、覆盖或提交别人的未完成改动。
3. 明确本任务的负责人、目标、文件范围、依赖和验收方式。一个人或 AI 可以负责多个任务，但每个独立任务分别提交 PR；同一任务的修正继续原分支。
4. 根据已有授权自主实现和自检。多人协作流程不要求每个小决定都向用户询问，也不自动授权给其他会话发消息或创建额外 AI；实际调度遵守用户授权及所用工具的规则。

## 任务分工

以下是可采用的拆分方式，属于示例，不代表已经有人领取任务。

| 任务方向 | 主要范围 | 交接重点 |
| --- | --- | --- |
| 界面与交互 | `css/rogue.css`、`script/rogue/rogue.ui.js` | 页面层级、返回、滚动与焦点、日夜与屏幕尺寸 |
| 玩法与内容 | `script/rogue/` 中的行动、地图、战斗、聚落和内容模块 | 行动结果、数值、存档兼容、确定性与可通关性 |
| Android 集成 | `android/web/`；原生 Java、清单及构建脚本按 `AGENTS.md` 和明确授权范围处理 | 离线加载、系统返回、备份恢复、WebView 兼容 |
| 测试与核验 | `scripts/test-*.mjs`、明确标注的夹具、核验文档 | 独立复现、回归结果、实际测试提交与环境 |
| 集成与发布 | PR 审核、合并、版本准备和 Release | 合并顺序、组合回归、原签名、附件下载校验 |

按可单独验收的用户行为拆任务，例如“简化仓库存取”和“扩充荒野事件”可分别开发。需要共用同一段界面、同一个存档结构或同一个接口时，先确定接口和合并顺序，再并行实现各自部分。

`script/rogue/lang/zh.js`、`rogue.num.js`、`rogue.state.js`、`rogue.save.js`、`index.html` 和维护文档容易被多个任务同时修改。任务卡须列出这些共享文件及预计改动，避免多人同时重写同一段。新增翻译 key 先列清单，玩法与 UI 先约定行动参数、返回值及显示数据。需要调整范围时更新任务卡，在自己的分支完成必要改动；不越过其他分支直接修其工作目录。

任务记录以对应 Issue 正文、PR 正文或已授权的任务消息为准。创建 PR 后，在正文补齐任务卡；没有必要为每个任务另建一个共享进度文件。建议采用以下格式：

```markdown
任务编号 / 标题：
负责人 / 会话标识：
目标与验收条件：
本任务不包含：
起点提交：
工作目录与分支：
计划修改文件：
共享文件、接口与翻译 key：
依赖 PR 与合并顺序：
实际测试命令、结果与所测提交：
已知限制与待处理事项：
审核人 / 集成负责人：
```

## 独立目录与分支

- 每个并行任务使用独立 clone 或 Git worktree。不能让多个 AI 在同一个工作目录切分支、改文件、暂存或提交。
- 分支从最新 `origin/main` 派生，命名为 `codex/<task-id>-<short-name>`，一项任务一个分支。外部贡献者可在自己的 Fork 使用同样命名，并向本仓库 `main` 提 PR。
- 依赖另一任务时，在任务卡和 PR 中明确。可等待依赖先合入，或从依赖分支派生并将 PR 先标为 Draft；依赖合入后更新分支、确认差异只包含本任务，再请求审核。
- 不在 `main` 上直接开发，不强推共享分支或 `main`。更新已公开任务分支优先合并最新 `origin/main`，保留已审核的历史；不擅自重写别人的提交。
- worktree 共用 Git 对象与引用，但文件各自独立；更新、归档及删除只操作本任务目录。AI 工具有托管 worktree 能力时，按工具规则创建和回收。

下面是已有本地仓库、工作区干净时的单任务示例；并行任务应先进入各自独立目录。任务名按实际内容替换。

```powershell
git status --short
git fetch origin
git switch -c codex/task-ui-storage origin/main
```

若当前目录已有其他任务改动，保留原状，改用新的 clone 或 worktree；不要用重置、清理或自动 stash 来挪走别人的工作。

## 实现、验证与提交 PR

1. 实现本任务，保持 `AI_README.md` 中的代码、界面、离线与许可边界；中文 UI 字符串仍走独立字典。存档升级、普通模式隔离和两据点规则不能被任务拆分遗漏。
2. 运行与改动相符的检查，记录命令、结果、所测提交与环境。测试失败须修复或如实标明原因；未测项不能写成通过。需要测试 Android 资源时先生成静态资源，不提交生成目录。
3. 至少执行 `AGENTS.md` 要求的三项回归：`node scripts/test-rogue.mjs`、`node scripts/test-rogue-issues.mjs`、`node scripts/test-rogue-storage.mjs`。UI 改动另遵守已有真实按钮完整通关要求，保留日夜、短屏、大字、返回、遮挡和存档隔离核验；声明夹具的边界测试与新局通关分别报告。纯文档修改另检查内容、链接与 diff，无需完整通关或生成安装包。
4. 检查差异，只暂存本任务文件；分成便于审核的提交。不得混入密钥、令牌、个人存档、缓存、工具依赖或其他任务产物。
5. 推送任务分支，向 `main` 提 PR。标题描述具体变化，正文写问题、实际行为、文件范围、依赖、验证结果和限制；不把计划当成已完成。

本任务的提交示例，文件列表以实际范围为准：

```powershell
git diff
git add -- css/rogue.css script/rogue/rogue.ui.js
git diff --cached --check
git diff --cached --stat
git commit -m "Improve survival storage navigation"
git push -u origin HEAD
```

PR 正文使用 GitHub 表单，或先写到本地文件再传给 `gh pr create --body-file`，保留真实换行。没有主仓库写权限时推送到 Fork，再提交跨仓库 PR；公开仓库本身不授予写权限。

## 审核、冲突与合并

- 指定一名当前任务实现者之外的审核人，可为开发者或被授权负责审核的另一个 AI。审核以完整 PR 差异和实际验证为依据；实现者自检不能冒充独立审核。
- 审核关注功能、正常操作路径、样式一致、旧档、普通档原始字节和离线资源，也检查是否混入任务外改动。提出具体文件和复现方式，避免只有“已看过”的结论。
- `main` 或依赖变化后，作者在自己的目录整合更新；冲突逐段保留双方意图，不能整份选择某一方来抹掉另一任务。解决后重新运行受影响检查，更新 PR；后续修改影响原审核结论时重新审核。
- 集成负责人确认依赖已按顺序合入、问题已解决、相关检查通过且有独立审核记录，再将 PR 合入 `main`。没有独立审核时保持 PR 待审，其他不依赖审核的工作可以继续；不把暂存分支当成已合入主线。
- 多个 PR 分别通过后，还需在组合后的主线或候选集成提交上验证共同影响的路径。例如补给模型和仓库 UI 分开修改时，最终须一起验证实际补给、存取、回合与刷新，不能仅复用各自旧结果。
- 合并方式由集成负责人按仓库实际设置选择，确保目标为最新主线且不覆盖新提交。完成后记录合并提交、待发布变更及尚未验证项，再清理自己的分支 / worktree。

仓库管理员可为 `main` 配置保护规则，要求 PR、至少一名审核及实际存在的必要检查，并禁止强推。本文规定协作流程，不代表 GitHub 上已经开启这些设置；AI 不应声称文档本身能强制拦截推送，也不自行修改成员权限。

## 统一版本与发布

1. 当轮只设一个发布负责人，可由已授权的维护 AI 担任。任务作者提交验证充分的 PR 和变更要点，正式版本号、Android `versionCode`、最终更新记录、发布元数据与签名包由发布负责人统一协调。
2. 任务分支不各自递增版本、不各自上传正式 APK。合并代码也不自动意味着立即发包；多个兼容修复可合成一次发布，纯文档变更无需升级应用版本或新建 Release。
3. 发布负责人从最新集成主线建立 `codex/release-<version>` 分支，完成版本准备与校验后提交发布 PR；审核合入后，在实际合并提交上构建 / 复核，创建对应版本标签并发布。若合并后又改了代码或版本信息，按 PR 流程更新并重测，不能让源码标签和安装包错位。
4. 正式签名仍由私有 `.local/signing/` 保管，不因多人协作公开或复制给贡献者。测试人员可以验证网页或自行测试构建，不能把其他签名的包当成可覆盖正式版的安装包。
5. 按 [RELEASING.md](RELEASING.md) 完成版本、签名、资源、源码标签、四个附件与匿名下载哈希验证，保留历史 Release。只发布已完成组合验证的提交，准确说明未做的真机检查。

## 给下一位 AI 的交接

换电脑或没有原聊天记录的新窗口，先读 [新环境接手](HANDOFF.md)，其中包含可复制的首条消息、工具准备、私有签名恢复及 PR / APK 状态区别。

交接时写明任务编号、工作目录、分支、起点和当前提交、PR 链接、已完成行为、实际测试、未提交文件、依赖与下一步。接手者先核实 Git 状态再继续，不能凭聊天标题猜分支，也不能把上一版测试报告当成本次结果。

这一流程用于后续各项开发与维护。普通代码任务完成到 PR 后，由负责集成和发布的维护者继续处理，避免多个执行者分别合并、改版本或发包。
